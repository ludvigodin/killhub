## Platform shape

| ID | Decision | Rationale |
|----|----------|-----------|
| D27 | **Two planes:** (1) durable **control plane** (Next.js + agent/harness workers) · (2) **one disposable Microsandbox microVM per job**. There is no separate Explore VM vs Test VM — explore and test share that same sandbox. | Operator choice: same disposable compute for discovery and runtime; avoids dual-VM cost and drift |
| D28 | **Plane 1 owns Jobs API + SSE** (Next.js). It starts the plan loop and launches/destroys the disposable sandbox via the harness. `explore/` is a same-host worker/library under Plane 1, not a disposable VM and not a separate plane. | Durable job state cannot live in an ephemeral sandbox |
| D1 | ~~Three planes: Next.js · Explore Sandbox · Test VM~~ → **superseded by D27** | — |
| D2 | ~~Plane 1 does not run the agent or provision VMs~~ → **superseded by D28** (Plane 1 owns orchestration; browser still must not hold secrets) | — |
| D3 | ~~Plane 2 owns plan loop and harness~~ → **superseded by D28** (plan loop + harness run on the control plane) | — |
| D4 | Disposable Microsandbox per job on Vultr VX1 — **retained**; clarified by D27 that this single sandbox is both explore and test | Ephemeral KVM isolation; destroy on `completed` / cancel / fail / absolute expiry (D37, D41) |
| D5 | ~~Primary v1 intents: **`git_mcp` \| `webapp`**; unknown intents blocked/flagged~~ → **superseded by D34** | — |
| D34 | Environment Agent **decides** how to demonstrate the repo. Prefer **`git_mcp`** or **`webapp`** when those fit; otherwise invent a minimal **`demo`** (e.g. serve a lone `.txt` / puzzle as a tiny HTTP page or scripted verify) and put that plan in `environment_profile.json`. Hard-fail only when no verifiable demo can be launched within caps — not merely because the repo is not MCP/webapp. Readiness for `demo` = the profile’s declared probe (typically HTTP 200 or a command exit 0 with logged evidence); still **verifiable execution**, not a chat description. **Outcome honesty** required by D54 — a generated demo must not be labeled as original-application success. | Operator wants agent judgment: “bring it up somehow” including edge repos |
| D6 | Canonical artifact: **`environment_profile.json`** (runtime). Bootstrap create uses a separate Killhub-owned bootstrap profile (D36). Versioned executable schema: **D51**. Profile **revisions** and current pointer: **D64**. | Clear handoff from discovery to sandbox provisioning |
| D51 | **Versioned executable profile schema (`schema_version`).** Runtime (and bootstrap) profiles are a complete contract: `services[]` (name, image/package, ports, health, env, depends_on), `commands[]` / install/run entries with **`cwd`**, argv/shell, env, timeout; **process supervision** (`supervise`: oneshot \| restart, stop signal, readiness delay); **probes** with explicit types. For MCP: required **`mcp.transport`**: `stdio` \| `streamable_http` (and optional URL for HTTP). **`stdio` readiness** is not an HTTP ping — Plane 2 runs an **in-guest MCP verify helper** that launches the server subprocess, speaks JSON-RPC over stdin/stdout (`initialize` → `notifications/initialized` → `tools/list`), and returns structured evidence. Schema lives in-repo (`schemas/environment_profile.v1.json`); breaking changes bump `schema_version`. | PROFILE was underspecified; MCP stdio ≠ HTTP healthcheck |
| D36 | **Bootstrap sandbox before discovery (extended by D69).** Plane 1 creates the job’s microVM from a Killhub-owned, schema-valid **bootstrap profile** (`intent: bootstrap`, defaulting to the **pre-baked Ubuntu 24.04 detonation base image** per **D69**). Inspection runs inside that VM. The agent then writes the **runtime** `environment_profile.json` and `DynamicInstallSpec`. For most targets (Node/Python/MCP), provisioning continues **in place** on the unified Ubuntu 24.04 detonation image without replacement; if an explicit custom `oci_image` override is required, harness **replaces** the same job’s sandbox (stop+remove bootstrap → create with new image → re-clone at the **resolved commit** — D62, and re-layer/inject sensors, `mitmproxy` CA, mounts, canaries, and IPC) — **never two concurrent microVMs for one job** (D27). Invalid **runtime** profiles must not start provision/install; bootstrap create is exempt because the bootstrap profile is trusted and pre-validated. Replacement inherits the original job `expires_at` and records a new **sandbox generation** (D64). | Breaks inspect↔create circular dependency while preserving Ubuntu 24.04 guest sensors & single-VM invariant |
| D64 | **Profile revisions + sandbox generations.** Persist every accepted profile as an append-only **revision** (`job_id`, `revision`, `phase`, `profile`, …) with `Job.current_profile_revision`. Persist every create/replace as a **sandbox generation** (`job_id`, `generation`, `environment_id`, `image`, `expires_at`, `state`, per-generation `destroyed_at`) with `Job.current_sandbox_generation`. Job-level `sandbox_id` / `destroyed_at` always describe the **current** generation (or final confirmed absence). When a bootstrap VM is removed during replace, set **that generation’s** `destroyed_at` and `state=replaced` — do **not** set job-level `destroyed_at` while a replacement is alive. Replacement must reuse the original job `expires_at` (never extend). Receipt history cites revision + generation ids. | One-row-per-job cannot represent bootstrap→runtime repairs or replacement history the receipt promises |
| D62 | **Resolved commit is mandatory; original_application launches the built checkout.** After the first successful clone, every job persists `resolved_commit` (full SHA). Runtime `source.commit` is **required** (not optional). Every re-clone (including after image replace) must check out that exact SHA. Claiming `verification.kind=original_application` requires launching the **built tree from that checkout** (local `node`/`python`/binaries under the workdir or packages already installed into that tree). Do **not** satisfy original-application readiness by `npx -y <unpinned-package>` or other commands that resolve/install a package absent from the local checkout/lockfile. Fixtures pin SHAs before step 11 ([plan/10b-pin-fixtures.md](plan/10b-pin-fixtures.md), D53). | Readiness must prove the inspected source; unversioned registry launches can retrieve different code |
| D22 | Plane 2 runtime = **[Microsandbox on Vultr Cloud Compute](https://docs.vultr.com/how-to-set-up-agent-sandboxing-on-vultr-cloud-compute)** (`msb` / SDK over KVM+libkrun) | Official Vultr agent-sandboxing path |
| D24 | **Public / demo control plane** runs on **Vultr Cloud Compute**; local `docker-compose` remains for development only | Vultr is the orchestration fabric, not only sandboxes |

| D8 | Plan loop may draft/validate the **runtime** profile before provision/install; sandbox **create for inspect** uses the bootstrap profile (D36). Install/launch require a validated runtime profile + harness. | Spec first for mutations; bootstrap is the only pre-discovery create |

| D29 | **No install allowlist in v1.** Any OCI image Microsandbox can boot + any install/run commands from the profile may be attempted; **failures are flagged** (job error / unsupported outcome), not silently invented into success. Still never inject Killhub secrets into the sandbox. | Match “everything Vultr/Microsandbox can run”; honesty over false green |
| D10 | Repair/readiness retries capped by **`MAX_REPAIR_ATTEMPTS`** | Bound cost and infinite loops |
| D11 | Vuln findings are **reported**, not auto-patched; findings and optional assessment failures must **not** invalidate readiness evidence. Terminal outcome for advisory-only findings is governed by the gate table (**D66**) — by default they do **not** block `completed`. | Visibility without erasing probe proof |
| D33 | **Vulnerability & detonation posture in v1 (extended by D73):** always run **SCA / lockfile / known-advisory scans** + AI `vuln_review`. **Do not** weaponize CVEs against non-target infrastructure or run generic web pentest suites. **Containment probes (D26)** prove sandbox isolation. For MCP targets, **Discovery (`@modelcontextprotocol/inspector` + SDK fallback) → Test-Planner Agent → Monitored MCP Detonation (D73)** is a first-class workflow producing a structured **Detonation Verdict JSON** mapped to 16 MITRE ATLAS tactics and OWASP MCP Top 10. | Combines safe non-weaponized SCA with active behavioral MCP detonation & telemetry |
| D35 | **MCP Discovery & Assessment (promoted to first-class pipeline by D73).** For `git_mcp` and MCP registry targets, Discovery (`@modelcontextprotocol/inspector --cli --format json` + Python MCP SDK fallback) runs automatically after launch to enumerate capabilities (`initialize`, `tools/list`, `resources/list`, `prompts/list`, `t0_tools_sha256`) and feed the **Test-Planner Agent** (**D73**). `mcp.security_assessment` in `environment_profile.json` may still customize probe depth/options; findings stream into `VulnReport` & `DetonationVerdict` and never invalidate `readiness` (D30 / D37). Tooling is pre-baked in the Ubuntu 24.04 image or preinstalled before Phase 2 (D63, D69). | Makes MCP capability discovery and behavioral detonation standard for MCP targets while keeping readiness independent |
| D30 | **`git_mcp` readiness** = real **MCP handshake** that can list tools (not merely process-alive or HTTP ping) | Proves the MCP server speaks the protocol |
| D31 | **Screenshots are optional.** Capture when useful (e.g. HTTP webapp verify); skip for CLI-only MCP or early fail. Missing screenshots must **not** invalidate readiness or block `completed`. | Not every job has a meaningful still |
| D37 | **Separate readiness from job completion.** `readiness` is probe evidence (`passed` / probe / detail) set when the profile probe succeeds. Terminal success status is **`completed`**, reached only after bounded report generation (SCA + `vuln_review`, optional MCP assessment), artifact capture, and sandbox cleanup. Do **not** destroy the sandbox merely because readiness passed. Destroy on `completed` \| `failed` \| `cancelled` \| absolute expiry (D41). Findings / optional assessment failures do not clear `readiness.passed`. Gate outcomes (D66) may fail the **job** without clearing readiness evidence. | Prevents premature destroy when “ready” meant both probe-ok and job-finished |

## API and realtime

| ID | Decision | Rationale |
|----|----------|-----------|
| D12 | Jobs are **server-owned**; disconnect ≠ cancel | Long pipelines survive tab close; cancel is explicit `DELETE` or timeout |
| D13 | Dual channel: **poll `GET /jobs/{id}` + SSE `/events`** must stay consistent | Robust UI + live updates |
| D14 | ~~SSE types: `status`, `progress`, `log`, `screenshot`, `error`~~ → **extended by D49** (those five remain; evidence types added) | — |
| D49 | **Structured evidence stream + job receipt.** SSE types: `status` · `progress` · `log` · `screenshot` · `error` · **`span`** · **`finding`** · **`containment`** · **`lifecycle`** · **`gap`** (D67). Keep-alives (D50) may use comment frames or empty `progress` heartbeats. Every job produces a durable **receipt** on Plane 1 that outlives the sandbox: profile revision(s), readiness, findings, containment/network probe results, sandbox generation lifecycle (`created` / `replaced` / `destroyed`), outcome gates, and `vuln_review` citations. Destroy evidence is required on every terminal path. Receipt is written **before** terminal status, including on cancel (D61). | Operators need an audit dossier, not only a progress bar |
| D50 | **SSE keep-alives** during long install/verify/scan steps (at least every ~15s while the stream is open) so clients do not appear stalled | Long Microsandbox steps otherwise look dead |
| D15 | Public **HTTPS `github.com`** URLs and validated **MCP registry targets** (`npm:<pkg>@<ver>`, `pypi:<pkg>==<ver>`, or pinned fixture IDs resolved via `DynamicInstallSpec`) in v1; reject arbitrary URLs/schemes with `400` | Supports both GitHub repos and MCP registry post-install detonation while preventing SSRF |
| D40 | **Public demo admission controls.** Per-job CPU/memory/timeout caps do not bound aggregate demand. Plane 1 enforces: **global concurrency** (`MAX_CONCURRENT_JOBS`), a **bounded queue** (`MAX_QUEUED_JOBS`), **request throttling** (per-IP / global rate limits on `POST /api/jobs`), **per-job and rolling inference budgets** (token/wall-clock), and **disk/log caps** (profile/screenshot/event retention sizes). Reject with `429` (rate / inference budget) or `503` (concurrency / queue full) and a clear error body — never silently drop. | Anonymous access needs hard admission, not only per-sandbox limits |
| D45 | **Plane-1 pre-flight before bootstrap sandbox create.** After URL validation + admission (D15, D40), run cheap checks on the control plane (and/or read-only GitHub metadata): rate/abuse already applied; optional known-malicious dependency / advisory pre-screen when cheap; reject or short-circuit with findings **without** creating a Microsandbox when pre-flight hard-fails. Soft signals may continue into the job with findings attached. | Avoid burning VX1 for obviously hostile or invalid intakes |
| D52 | **Python sidecar owns job state.** Close the Next.js↔`explore/` non-decision: **`explore/` is a same-host localhost sidecar** that owns the durable ledger and workers. Next.js is a thin public edge (UI + `/api` proxy) and does **not** hold the job dictionary. Internal Worker API (loopback + `INTERNAL_API_TOKEN`): `POST /internal/jobs`, `GET /internal/jobs/{id}` (snapshot), `GET /internal/jobs/{id}/events` (SSE), `DELETE /internal/jobs/{id}` (cancel), plus screenshot routes as needed. Define and freeze this interface **before** N1/E1. | Next.js and Python cannot share an in-process dict; one state owner avoids split-brain |
| D55 | **SSE cursor contract.** Snapshot includes `event_cursor` (last durable `event_id`). Clients hydrate snapshot then subscribe with `Last-Event-ID` / `?after=`. Retain events for `EVENT_RETENTION` (at least job active lifetime + configurable post-terminal window) subject to byte-budget pruning rules in **D67**. Unknown/expired cursor → `410` or SSE `error` with `code=cursor_expired`; client must re-snapshot and resubscribe — never silently skip a gap. | Prevents missed events between hydrate and subscribe |
| D67 | **Event retention is contiguous; no silent holes.** When `MAX_JOB_LOG_BYTES` is exceeded, prune a **prefix** of the oldest durable events for that job (contiguous from the start of the retained sequence). Never delete middle events while keeping older and newer neighbors. After a prune, insert exactly one durable `gap` event (or tombstone with `type=gap`) documenting `{ pruned_before_event_id, pruned_after_event_id?, bytes_freed }` so replay after that point remains contiguous. A fresh snapshot’s `event_cursor` is the last **retained** event; SSE replay from a valid cursor is gap-free forward. Cursors that fall inside a pruned range are expired (D55). Active-job retention promise means the **current retained window** is complete — not that every historical byte since create is forever available once budgets bite. | Dropping selected old payloads left holes after an otherwise valid cursor |
| D61 | **Cancel ordering: request → freeze → finalizer → terminal.** On `DELETE`: (1) set `cancel_requested_at` immediately and freeze **ordinary** workers (plan loop, install, repair, assessment, non-finalizer status/progress/profile mutations); (2) enter bounded **finalizer** work while status is non-terminal (`finalizing` with cancel intent, or keep prior phase visibly frozen); (3) finalizer **may** write the allowlisted fields: `cleanup.*`, destroy/lifecycle evidence, `receipt`, cancel `log`/`span`, progress/current_step for cleanup only, and `status` transitions into `finalizing` then terminal `cancelled`; (4) persist receipt **before** setting terminal `cancelled`; (5) SSE stays open until terminal status. Repeated `DELETE` on already-`cancelled` is idempotent with the same terminal snapshot. Cancel during bootstrap/create aborts in-flight `msb create` (best effort) and destroys any partial sandbox via the same finalizer path. Supersedes the earlier D56 wording that set `cancelled` before receipt. | Receipt is mandatory on every path; early `cancelled` made finalizer writes and SSE closure ambiguous |
| D56 | ~~Cancel commits `cancelled` then allows only cleanup writes~~ → **superseded by D61** (ordering + explicit finalizer allowlist; idempotency retained) | — |

## Security

| ID | Decision | Rationale |
|----|----------|-----------|
| D19 | Killhub control-plane secrets **never** injected into sandbox `env` by default | Prevent key exfiltration via untrusted repos |
| D20 | Agent tools may only target harness / sandbox APIs — **never** execute untrusted repo install/run on the control-plane host | Discovery reads via clone/`msb` copy/exec inside the sandbox |
| D38 | **OpenCode lockdown & Plane 1 vs Plane 2 split (enforceable; extended by D71).** Plane 1 planners/reviewers (`Environment/Install Planner`, `Test Planner`, `vuln_review`) run under a **trusted system/managed config** (host-owned; outranks project/user config) that **denies** host `shell`, local edit/write of untrusted trees, arbitrary providers/plugins/MCP, and non-Vultr inference (`provider.use` allows only Vultr Serverless Inference — D25), exposing **only** job-scoped harness tools (create/exec/copy/destroy/readiness/discovery helpers). Separately, **victim/detonation OpenCode** runs **inside Plane 2** (`/home/agent/.config/opencode/`, `/home/agent/.local/share/opencode/opencode.db`) talking exclusively to the **Plane 1 Host LLM Proxy** (**D71**) with a dummy token and exposed via **view-only `noVNC`**. Submitted repository files (`AGENTS.md`, `.opencode`, prompts, scripts) and MCP tool outputs are **untrusted input** — never loaded as Plane 1 host authority. **Playwright browser execution for stills runs inside Plane 2**; host paths for copy tools are restricted by **D60**. | Prevents host shell/config hijack on Plane 1 while enabling realistic in-VM OpenCode MCP detonation in Plane 2 |
| D60 | **Harness `copy_in` / `copy_out` are path-restricted.** Agent-facing and internal harness copy APIs must not accept arbitrary host paths. **Host sources for `copy_in`:** only Killhub-owned helper trees (e.g. `explore/helpers/`, trusted verify/assessment payloads) under an allowlisted absolute root, resolved with `realpath`, rejecting `..`, symlink escape outside the root, and non-regular files unless explicitly allowlisted. **Host destinations for `copy_out`:** only the server-selected per-job artifact directory (`storage/screenshots/{job_id}/`, `storage/artifacts/{job_id}/`, or equivalent ledger-owned paths). Guest paths stay inside the sandbox workdir/policy. Enforce max bytes per copy and per job (`MAX_COPY_BYTES` / disk caps — D40). Overwrite of host files outside those dirs is forbidden. Job scoping alone is insufficient. | API previously exposed arbitrary paths while D38 still allowed agent-facing harness tools |
| D21 | Prefer non-root in sandbox; no Docker socket mount from control plane | Reduce breakout risk |
| D23 | Harness drives Plane 2 via **`msb` CLI / Microsandbox SDK** (create / exec / copy / stop / remove); OpenCode may use only harness-scoped MCP tools allowed by D38 | Job-owned lifecycle stays in harness; agent MCP is additive and policy-gated |
| D59 | **Vultr MCP + CLI are the operator/agent interface to Vultr.** Building and operating Killhub must use: (1) **Vultr MCP** (`https://mcp.vultr.com/mcp`) for read-only inventory/oversight when available; (2) **`vultr-cli`** (or Vultr API with `VULTR_API_KEY`) for mutating Cloud Compute; (3) **`msb` CLI / Microsandbox SDK** for Plane 2 lifecycle — optionally **`microsandbox-mcp`** for agent-assisted debug under D38. Do **not** substitute Docker-on-control-plane for Microsandbox, non-Vultr clouds for demo/VX1, or fake `msb` success. If MCP/CLI/credentials are missing, **stop and report** — do not invent a third path. Product harness remains D23 (`msb`/SDK). See [plan/VULTR.md](plan/VULTR.md). | Keeps agents on the real Vultr fabric instead of local mocks that break isolation claims |
| D26 | **Containment proof** is a first-class path — **extended by D58 / D65**. A timed-out loop alone only proves timeout enforcement, not isolation. | Isolation is only demonstrable if unsafe execution is visible and contained |
| D58 | **Containment evidence matrix (extended by D72).** Before claiming isolation, the harness must record structured evidence for: (1) **timeout_enforcement** — adversarial loop absorbed by timeout / **3-Layer Kill Switch (D72)**; (2) **host_access_denied** — guest cannot reach host/control-plane/management destinations (aligns D39); (3) **sibling_access_denied** — cannot reach another job’s sandbox; (4) **host_liveness** — host/control-plane remains healthy during the probe (no crash/OOM attributed to the guest). Stream as `containment` SSE / `DetonationVerdict.containment_proof` / `JobReceipt` fields. Missing dimensions ⇒ containment claim incomplete, not “proven.” Not CVE exploitation of the submitted app (D33). Evidence quality rules: **D65**. | Broader isolation claims need multi-axis evidence incl. 3-layer kill switch |
| D65 | **Containment probes need positive controls and policy-vs-infra distinction (extended by D70/D71).** Failed fetches alone are not isolation proof. For each deny claim: (1) use **known-live targets** (control-plane URL / management endpoint that Plane 1 confirmed reachable from the host during the same job window); (2) run a **positive control** from a permitted vantage (e.g. host-side fetch succeeds) before treating guest failure as deny; (3) classify outcomes as `policy_denied` \| `infra_error` \| `tooling_missing` \| `inconclusive` — only `policy_denied` (with live target + positive control) counts toward `host_access_denied` / sibling deny; (4) probe control-plane denial during **both** Install/Monitored Detonation (TAP/`mitmdump` active) and Strict Offline Verify so blanket offline mode cannot masquerade as CP isolation; (5) verify `AF_VSOCK`/UDS/`mgmt0` only exposes the Host LLM Proxy & telemetry receiver (never Jobs API/`msb` mgmt); (6) deliberate containment/canary probe traffic and planted canary values used by the harness must be **excluded** from unexpected-canary findings (tag probe sessions; canary scanner ignore-list for harness-owned probe IDs). | Distinguishes real policy denial from DNS/offline/tooling failure |
| D39 | **Plane 2 network policy is explicit and tested (extended by D70/D71).** Microsandbox defaults allow public-internet egress and deny host/private/metadata — that is **not** sufficient when the control plane has a public URL. Every sandbox create attaches a **host-side TAP bridge + firewall** that: (1) enforces sibling isolation; (2) **denies general guest IP egress** to control-plane destinations (public demo hostname/IPs, Jobs API ports) and to **Microsandbox management endpoints**; (3) **drops DoH/DoT/QUIC** (UDP 443, TCP 853, known DoH resolvers) so all HTTP/S + DNS must traverse `mitmdump` (**D70**); and (4) permits **only hypervisor-constrained IPC** (`AF_VSOCK` control + NDJSON telemetry, or UDS/`mgmt0` fallback for Host LLM Proxy and view-only `noVNC` bridge — **D71**). Ship `network_probe` verifying denial per **D65**. Gate outcomes for successful CP access: **D66**. | Replaces unbridged default NAT with inspectable TAP + hypervisor IPC while enforcing CP/mgmt denial |

## MicroVM Detonation, Network Interception, IPC, Kill Switch & ATLAS/OWASP Pipeline (D69–D74)

| ID | Decision | Rationale |
|----|----------|-----------|
| D69 | **Unified Ubuntu 24.04 Detonation MicroVM Spec, Mounts, Seeds & Guest Sensors.** Plane 2 standardizes on a pre-baked **Ubuntu 24.04** microVM image containing `python`, `pip`, `uv`, Node 22+, `git`, `strace`, `OpenCode`, `@modelcontextprotocol/inspector`, and `noVNC`, provisioned dynamically via the Environment/Install Planner's validated `DynamicInstallSpec` (`schemas/dynamic_install_spec.v1.json`) for cloned GitHub repos or MCP registry targets (`npm:`, `pypi:`, pinned fixtures). **Mandatory mounts & seeds:** read-only rootfs + OverlayFS writable layer (`upperdir` diffed for filesystem tamper); baked `mitmproxy` root CA + TLS env vars (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`); size-capped `/workspace` with `.env` canary; seeded `/home/agent/.ssh` & `/home/agent/.aws` canary tokens; pre-seeded `/home/agent/.local/share/opencode/opencode.db`, `/home/agent/.config/opencode/`, and `.gitconfig` pointing to the Plane 1 Host LLM Proxy; writable `/run/mcp-package-cache` tmpfs; isolated `/dev/vsock` (or UDS/`mgmt0`) IPC. **Guest sensors:** `strace` syscall tracing, OverlayFS `upperdir` diff, MCP stdio/HTTP JSON-RPC wire tap, cgroup v2 `memory.events`/`pids.events`, and `package_sha256_before`/`after`. | Eliminates image-replace loss of sensors and guarantees uniform telemetry, mounts, and canary placement across all targets |
| D70 | **Host TAP Bridge, `mitmdump` HTTP/S+DNS Interception, DoH/DoT/QUIC Drop, Real-Time Canary Blocking & Optional PCAP.** Plane 2 guest networking attaches to a per-job host-side **TAP bridge** managed by Plane 1/VX1 harness: (1) transparent `mitmdump` intercepts HTTP/HTTPS (using the guest-baked `mitmproxy` CA) and DNS queries; (2) firewall rules drop **DoH** (known DoH resolver IPs/endpoints), **DoT** (TCP/853), **QUIC/HTTP3** (UDP/443), and raw bypass egress to prevent encrypted/alt-transport evasion; (3) `mitmdump` + DNS + wire-tap hooks perform **real-time canary exfiltration blocking** (aborting outbound requests containing planted canary patterns and emitting `finding`/`containment` events immediately); (4) optional `tcpdump` captures bounded per-job PCAPs to `storage/artifacts/{job_id}/` when enabled; (5) Phase 1 allows registry/git via TAP+`mitmdump`, Phase 2a runs **Monitored Detonation Egress**, and Phase 2b drops all remaining egress (loopback only) for static offline containment verification. | Makes network/DNS exfiltration observable and blockable in real time during detonation without weakening CP/sibling isolation |
| D71 | **`AF_VSOCK` / UDS / `mgmt0` IPC, In-VM OpenCode + View-Only `noVNC`, & Plane 1 Host LLM Proxy Key Isolation.** Hypervisor-constrained IPC uses **`AF_VSOCK`** (dedicated control channel + NDJSON telemetry stream) with **UDS / `mgmt0`** fallback when the host kernel/hypervisor topology requires it. Key isolation is **demonstrably verifiable**: `/proc/*/environ` inside Plane 2, `/home/agent/.config/opencode/`, and `opencode.db` contain only the dummy token, while `mitmdump`/proxy logs confirm real keys never traverse Plane 2. | Allows genuine in-VM OpenCode MCP detonation and live operator visibility (`noVNC`) with zero risk of leaking `VULTR_INFERENCE_API_KEY` |
